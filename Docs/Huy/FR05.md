## 1. Mô tả
Hệ thống kiểm tra một Pull Request có làm tài liệu hiện có bị lỗi thời hay không (documentation drift). Người dùng nhập số Pull Request. GitHub Integration Service đọc PR và các file thay đổi (kèm diff) từ GitHub, chạy Code Analyzer trên mã nguồn trước thay đổi (merge base) và sau thay đổi (head), lấy README cùng các file Markdown của repository, rồi gửi tất cả sang AI Service. AI Service xác định các thực thể mã nguồn đã thay đổi, tìm những đoạn tài liệu còn nhắc tới chúng, sau đó tạo báo cáo drift. Mỗi phát hiện (finding) trong báo cáo có loại, độ nghiêm trọng, độ tin cậy và bằng chứng.

```
PR files (patch + kết quả analyzer ở base/head)
  -> LD-146 drift_changes.py   thực thể thay đổi: added / removed / renamed / signature_changed / behavior_changed
  -> LD-148 drift_affected.py  tài liệu đã lưu + Markdown của repo có nhắc tới các thực thể đó
  -> LD-147 drift.py           findings: loại, độ nghiêm trọng, độ tin cậy
  -> LD-149 drift_evidence.py  code diff, đoạn tài liệu, commit, Jira ticket
```

| **FR-AI-05.6** | Lưu báo cáo để xem lại theo repository và theo số PR. Chỉ người tạo báo cáo mới được đọc báo cáo đó. |

## 4. Luồng chính
1. Người dùng chọn repository đã kết nối, nhập số Pull Request và bấm **"Analyze drift"**.
2. GitHub Integration Service đọc PR và danh sách file thay đổi kèm diff (nhiều trang), rồi tìm merge base của PR.
3. Service tải nội dung các file Python/Java ở merge base và ở head (tối đa 100 file), rồi gọi Code Analyzer `POST /api/v1/analyze-repo` cho cả hai phía để có `before` / `after`.
4. Service đọc README và các file Markdown của repository ở commit head (tối đa 30 file, bỏ qua `node_modules`, `target`, `dist`...).
5. Service gọi AI Service `POST /drift/analyze` với PR, các file thay đổi, Markdown của repository và tài liệu đã lưu **của repository đó**.
6. AI Service xác định thực thể thay đổi (LD-146), tìm tài liệu bị ảnh hưởng (LD-148), phân loại và chấm điểm (LD-147), sinh bằng chứng (LD-149), sau đó lưu báo cáo.
7. Người dùng nhận báo cáo với trạng thái `drift_detected` hoặc `no_drift`, rồi xem lại sau qua danh sách báo cáo.

## 5. Luồng lỗi

| Trường hợp | HTTP | Kết quả |
| :--- | :--- | :--- |

## 6. Quy tắc nghiệp vụ
* Diff của PR được tính từ merge base, nên mã nguồn "trước thay đổi" cũng được đọc ở merge base, không phải ở đầu nhánh `main`.
* **Độ nghiêm trọng:** xoá/đổi tên thực thể là High (endpoint là Critical); thay đổi chữ ký là Medium (endpoint +1; tài liệu vẫn nhắc tham số đã bị xoá +1); thay đổi hành vi là Low (docstring đổi +1; từ 15 dòng thay đổi trở lên +1); tên private `_name` -1.
* **Độ tin cậy** = match × method × location × certainty. Mức: high ≥ 0.75, medium ≥ 0.50 (giống LD-340).
* **Tránh báo nhầm:** chỉ khớp nguyên định danh; từ phổ biến (`add`, `run`) chỉ tính khi nằm trong code hoặc heading; tên method đứng riêng chỉ tính trong phần tài liệu của chính file đó; đường dẫn endpoint khớp mọi kiểu placeholder (`{id}`, `:id`, `<id>`).
* Chỉ kiểm tra tài liệu đã lưu của chính repository đó; tài liệu của repository khác bị từ chối kèm cảnh báo.
* Báo cáo được giữ trong bộ nhớ (500 báo cáo gần nhất) và mất khi khởi động lại. Lịch sử và việc xử lý drift thuộc LD-167.

---

## 7. Tiêu chí chấp nhận
* **AC-AI-05.1:** Một PR xoá, đổi tên hoặc đổi chữ ký của thực thể mà tài liệu còn nhắc tới sẽ tạo finding đúng loại (Referential / Signature / Semantic). PR không làm tài liệu lỗi thời thì trả về `no_drift`.
* **AC-AI-05.2:** Mọi finding đều có độ nghiêm trọng, độ tin cậy kèm `factors`, và ít nhất một bằng chứng code diff (`X1`) cùng một đoạn tài liệu (`D1`).
* **AC-AI-05.3:** Khi Code Analyzer lỗi, hệ thống vẫn trả báo cáo dựa trên diff và ghi lý do trong `warnings`.
