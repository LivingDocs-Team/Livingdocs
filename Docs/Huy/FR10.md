## 1. Mô tả
Kiểm tra và sửa việc lưu trữ evidence và submission. Lỗi được tái hiện trước, chỉ sửa những lỗi đã xác nhận. Kết quả kiểm tra: tài liệu và evidence của AI Service (lưu trong `DOCUMENTS_FILE`) **vẫn còn sau restart**. Các lỗi thật nằm ở 3 chỗ:
- **Evidence của version sửa/rollback:** version tạo khi owner sửa sau "changes requested", hoặc khi rollback, bị mất evidence. Vì vậy staff và manager không xem được bằng chứng của bản nộp lại (404).
- **Evidence/submission của PR #108:** dữ liệu chỉ nằm trong RAM của Code Analyzer, nên restart là mất hết; không có API để đọc lại; `EvidenceResponse` bị khai báo trùng.
- **Submit tài liệu mới:** tài liệu vừa sinh (`current_version = 0`, `pending_version = 1`) không submit được lần đầu (409).

```
Owner sửa / rollback -> version mới kế thừa evidence của version gốc (evidence_from_version)
                     -> staff: /review-evidence, manager: /evidence  -> 200 (trước: 404)
PR #108: POST /api/v1/evidences, /submissions -> SubmissionStore -> SUBMISSIONS_FILE (volume analyzer-data)
Workflow: create -> submit (pending_version 1) -> lưu DB -> staff review -> resubmit version mới
```

## 4. Luồng chính
1. Owner tạo workflow cho tài liệu vừa sinh và bấm **Submit**; workflow lưu `submitted_document_version = 1` vào database.
2. Staff nhận việc, xem review evidence của version 1 và yêu cầu chỉnh sửa (**changes requested**).
3. Owner sửa nội dung: AI Service tạo version 2, kế thừa evidence của version 1 (`evidence_from_version = 1`).
4. Owner nộp lại; staff xem review evidence của version 2 (200), duyệt; manager xem grounding evidence (200) và phê duyệt.
5. Khi rollback về một version đã duyệt, version khôi phục mang đủ evidence nên lại review được.
6. Với PR #108: tạo evidence, tạo submission từ các evidence đó, submit; sau khi Code Analyzer khởi động lại, evidence và submission vẫn đọc và dùng lại được.

## 5. Luồng lỗi

| Trường hợp | HTTP | Kết quả |
| :--- | :--- | :--- |
| Tạo submission với evidence không tồn tại | `400` | `{"detail": "Các Evidence ID sau không tồn tại: ['ev-nope']"}` |
| Submit submission không có evidence | `400` | `{"detail": "Cần ít nhất 1 evidence để thực hiện submit"}` |
| Evidence / submission không tồn tại | `404` | `{"detail": "Evidence không tồn tại"}` / `{"detail": "Submission không tồn tại"}` |
| Submit submission không ở trạng thái DRAFT | `409` | `{"detail": "Submission đang ở trạng thái ..., không thể submit"}` (đã SUBMITTED thì trả lại kết quả cũ, `200`) |
| Workflow submit tài liệu không có version nào | `409` | `{"message": "The document has no readable version."}` |
| Version không có review report trong toàn bộ lịch sử | `404` | `{"detail": "Review evidence is not available for this document version"}` |
| File `SUBMISSIONS_FILE` bị hỏng | — | File được đổi tên thành `*.corrupt-<thời gian>.json`, service chạy với dữ liệu trống |

## 6. Quy tắc nghiệp vụ
* Bản sửa tay giữ evidence của version gốc vì phần mã nguồn mà tài liệu mô tả không đổi; `evidence_from_version` cho reviewer biết evidence lấy từ version nào.
* Evidence được sao chép độc lập: sửa evidence của một version không ảnh hưởng version khác.
* Ghi file luôn atomic (file tạm + đổi tên), để khi gặp sự cố không bao giờ để lại file ghi dở.
* Docker Compose: AI Service lưu `DOCUMENTS_FILE` trên volume `ai-templates`; Code Analyzer lưu `SUBMISSIONS_FILE=/app/data/submissions.json` trên volume `analyzer-data`, thư mục `/app/data` thuộc user `analyzer` (không phải root).
* Đặt `DOCUMENTS_FILE` / `SUBMISSIONS_FILE` là chuỗi rỗng thì chỉ lưu trong bộ nhớ (dùng cho test).

## 7. Tiêu chí chấp nhận
* **AC-AI-10.1:** Tài liệu và evidence vẫn đọc được sau khi restart thật (2 tiến trình nối tiếp dùng chung `DOCUMENTS_FILE` / `SUBMISSIONS_FILE`).
